Language Models: Foundations

Softmax (Module 5) is the bridge: it's exactly what an LLM uses to pick its next word.

You already know how to write a program that produces text — a template engine, a report generator. Those work because you specified the rules. Language models solve a different problem: how do you get a machine to produce fluent, contextually-appropriate text when the "rules" of a natural language are too vast, irregular, and context-sensitive to hand-code? The approach that has actually worked at scale is to stop trying to encode the rules and instead let a model infer them from an enormous amount of example text, by training it on one very narrow, very learnable task: given everything written so far, guess the next word. Do that well enough, over enough text, and something that looks like "understanding" falls out as a side effect.

Formally, a language model predicts the next token given everything before it:

P(xₜ | x₁, …, xₜ₋₁)

Picture this as a function signature: it takes a sequence of tokens (text so far) and returns not a single answer but a full probability distribution over every possible "next token" in the vocabulary — closer to a method returning Map<Token, Double> than one returning a single Token.

The crucial property making this trainable at all: it's self-supervised — no human ever labels examples. Take any sentence from the internet — "the cat sat on the ___" — and the "label" (mat) is just the next word that was already there. Slide a window across a document and every position gives a free training example. This turns an unlimited supply of unlabeled text into an unlimited supply of labeled training pairs, which is why these models can be trained on a meaningful fraction of the internet.

Context determines everything

Because the prediction is conditioned on everything before it, the same literal prompt produces wildly different distributions depending on what surrounds it:

Context for "…pass me the ___"P(Salt)P(Pepper)P(Gun)
Family dinner scene0.540.330.13
Tense confrontation scene0.160.180.66

Nothing about the sentence itself changed — only the context feeding into P(xₜ|x₁,…,xₜ₋₁) changed, and that flipped the most likely answer entirely. A language model isn't memorizing "salt follows honey"; it's learning a function of the entire preceding context.

One trick, many tasks

Because next-token prediction is so general, an enormous range of NLP tasks reduce to "phrase it as a continuation problem":

TaskGoal
Sentiment analysisDetermine emotional tone/opinion
SummarizationCondense long text, keep key info
Question answeringAnswer based on context/knowledge base
Named entity recognitionIdentify/classify proper nouns (person, org, …)
Text classificationAssign categories/labels (spam, topic)
Machine translationTranslate between languages
Text generationProduce new coherent text from a prompt

If you know the value of a good abstraction — one interface, many implementations — this is the NLP equivalent: one pretraining objective turns out to be a sufficiently general primitive that translation, classification, and summarization all reduce to it.

Why text is a hard input to work with

Text is a uniquely inconvenient input format compared to structured data, for three compounding reasons:

  • Unstructured — no fixed schema, a sentence is just a variable-length string.
  • Ambiguous — the same token can mean entirely different things ("bank" = financial institution or riverbank), similar to overloaded method names that only resolve correctly at the call site.
  • Context-dependent — the same word shifts meaning depending on what surrounds it ("cold" = temperature or illness).

Text doesn't come with the fairly regular underlying alphabet audio or DNA has — which is exactly why "convert everything into numbers and let statistics/learning handle ambiguity" became the dominant strategy over hand-written rules.

Training & Inference

Predict-the-next-token, billions of times over — then decode one token at a time at inference.

The training pipeline, step by step

1. Collect a large text corpus. Common Crawl, Wikipedia, digitized books, WebText. The guiding principle is scale: hundreds of billions to trillions of tokens.

2. Tokenize. Raw text has to become integers before a neural network can touch it — it has no native notion of a "letter" or "word," only numbers. A tokenizer splits text into words, subwords, or characters and maps each to an integer ID from a fixed vocabulary table — think of it as an enum, and tokenization as the mapping from raw string to enum value. If you've written or used a compiler's lexer — turning source code into a stream of tokens like IDENTIFIER, PLUS, NUMBER before parsing — this is the same idea, except the "grammar" is far messier, so most tokenizers split on subwords: common words get their own token, rare words get broken into reusable pieces. A larger vocabulary means more tokens are available as single units, at the cost of a bigger lookup table and output layer.

3. Causal masking. At each position, the model may only see tokens that came before it — never after. This forces it to actually learn to predict the future from the past, rather than peeking at the answer in the rest of the sentence. Layered on top is an attention mechanism, letting each token look back across all previous tokens and decide, dynamically, how much to weight each one — each token issuing a search query against every earlier token's "profile" and pulling in a weighted blend of the most relevant hits.

4. Repeat, at massive scale. Applied across the entire corpus, billions of times, entirely self-supervised. This is why training a frontier model from scratch is enormously compute-intensive — why only a handful of well-funded labs pretrain foundation models, while everyone else fine-tunes an existing one, much like most engineers build on a database engine rather than writing their own.

Gotcha

The LLM's output layer is a softmax over the entire vocabulary — its size equals the vocabulary size, not the embedding dimension and not the context length. Every forward pass produces a full probability distribution over every token the model knows, most getting near-zero probability for any given context.

Inference: autoregression and decoding

Once trained, generating text is a pipeline: text → tokenizer → embedding lookup → decoder-only transformer → linear layer → softmax → a probability per vocabulary token. The embedding lookup turns each integer token ID into a dense vector — an array/dictionary lookup mapping token_id → float[d], where nearby vectors represent related tokens (more on this in §4). The linear layer at the end projects back up to vocabulary size, producing a raw score — a logit — for every possible next token; logits are unbounded, not yet probabilities. Softmax turns that vector of logits into an actual probability distribution.

  • Greedy decoding — always pick the single highest-probability token. Deterministic: same input, same output every time, like a pure function.
  • Autoregression — whatever gets generated is appended back onto the context, and the process runs again: "Once upon" → +"a" → "Once upon a" → +"time" — a feedback loop, similar to a REPL where each output becomes part of the input to the next call.

Pure greedy decoding is safe and reproducible, but tends to be repetitive — a purely deterministic function always returns its cached result, which is exactly what you don't want from something meant to write varied text.

Temperature: reshaping the distribution before sampling

Temperature reshapes the probability distribution before sampling, instead of always taking the single most likely token:

p(zᵢ) = e^(zᵢ/T) / Σⱼ e^(zⱼ/T)

zᵢ is the raw logit for token i, T is the temperature you choose at generation time. Dividing every logit by T before exponentiating compresses or stretches the gaps between logits: small T makes the biggest logit dominate more, large T squashes the differences toward zero. Softmax is monotonic — dividing by T never changes which token has the highest score, only how much more likely it is relative to the rest.

Worked example

Take the seven logits [2.0, 1.0, 0.5, 0.01, 3, 2, 1.5] — label them A through G. At T=1.0:

Tokenlogit ze^zprobability
A2.07.3890.165
B1.02.7180.061
C0.51.6490.037
D0.011.0100.023
E3.020.0860.449
F2.07.3890.165
G1.54.4820.100

Sum of e^z ≈ 44.722; each probability = e^z / 44.722 (e.g. E: 20.086/44.722 ≈ 0.449). Probabilities sum to 1.0.

Lower to T=0.5 (sharpening): every logit doubles before exponentiating: [4.0,2.0,1.0,0.02,6.0,4.0,3.0]. Sum of exponentials ≈ 543.838:

Tokenz/Te^(z/T)probability
A4.054.5980.100
E6.0403.4290.742

Token E now grabs 74.2% of the probability mass — up from 44.9% at T=1. Lower temperature concentrates probability on the front-runner.

Raise instead to T=2.0 (flattening): logits halve: [1.0,0.5,0.25,0.005,1.5,1.0,0.75], sum ≈15.973. Token E drops to 28.1%, and the weakest token D climbs from 2.3% to 6.3%. At higher temperature every token becomes more competitive.

So: T<1.0 sharpens toward the top candidate (more deterministic, less creative); T>1.0 flattens it (more random, more creative); T=1.0 leaves the raw distribution untouched. Temperature is often combined with top-k sampling (restrict to the k highest-probability tokens, like a LIMIT k on a ranked query) or top-p/nucleus sampling (keep the smallest set of top tokens whose cumulative probability crosses p) to avoid ever sampling a wildly implausible token even at high temperature.

Note

ChatGPT is not a raw LLM — it's an LLM wrapped with prompt engineering, RLHF fine-tuning/alignment (Reinforcement Learning from Human Feedback: an additional training phase nudging the model toward outputs human raters actually prefer), conversation-memory handling, tool integration, and safety layers on top. Next-token prediction is the engine; a lot of additional engineering surrounds it before you see a chat window.

3

Why RAG?

A plain LLM chatbot has structural blind spots RAG is built to patch.

A trained LLM is, in an important sense, a snapshot. All its "knowledge" is baked into billions of fixed numeric weights at the end of training — the same way compiling a program bakes a particular version of your business logic into a binary. Once that snapshot is taken, the model can't learn about anything that happened afterward, can't consult a document it never saw, and — since its answers come from statistical pattern completion rather than lookup — can't point to a specific source for a claim, even when it happens to be right.

Pitfall of a plain LLMWhy it happens
Static knowledgeTrained on fixed data; blind to anything after the training cutoff
HallucinationConfidently fabricates answers, especially on niche topics
Context window limitsHard cap on how much text can be passed in at once
Domain knowledge gapsGeneric pretraining lacks company-specific/technical depth
No source attributionDoesn't show where an answer came from
Low explainabilityHard to verify how an answer was produced

A few of these map onto things you already reason about. Context window limits are just a fixed-capacity buffer — like an array with a hard-coded max size — that the whole conversation has to fit inside. No source attribution and low explainability are the same complaint you'd have about a black-box function with no logging: it returns an answer, but you can't trace why. Hallucination happens because the model was never trained to say "I don't know" — it always produces some plausible-sounding continuation, so on unfamiliar territory it confidently generates something that merely looks right.

Two different fixes: RAG vs. fine-tuning

There are two structurally different ways to patch these gaps, mapping onto a trade-off you've likely made before: read fresh data at runtime from an external source, or bake the data into the deployed artifact itself.

RAGFine-tuning
MechanismRetrieves relevant external documents at query timeModifies the model's internal weights via further training
Model changesNone — cheap, easy to updateProduces a new tuned model; no external DB needed at inference
Best forEvolving data, agilityStable domains needing precision/consistency

RAG is like a service querying a live database on every request — update the underlying data and the next query reflects it, no redeploy, at the cost of retrieval infrastructure and extra latency. Fine-tuning is closer to compiling business rules directly into the binary — fast and consistent at inference, but updating means retraining and redeploying the whole model. Neither is strictly better: RAG wins when knowledge changes often or needs to be traceable to a source; fine-tuning wins when the domain is stable and you want behavior baked in without a runtime dependency. In practice the two are often combined.

4

The RAG Pipeline

An offline indexing phase, and an online query phase.

If you've worked anywhere near a search engine, the two-phase structure of RAG will feel immediately familiar:

  • Indexing (offline): documents → chunk & preprocess → generate embeddings → store in a vector database. The RAG equivalent of a web crawler building an inverted index ahead of time, before any user types a query.
  • Query (online): user question → embed the question → semantic search against the vector DB → ranked chunks → pass query + chunks to the LLM → generated answer. Like a search box hitting that prebuilt index — except the final step doesn't just return a ranked list, it hands results to an LLM to synthesize a written answer.

Chunking

An embedding model can only usefully represent a limited amount of text at once, and a long document usually mixes many topics — burying the one relevant paragraph in ten pages of unrelated material hurts retrieval precision the same way an overly long function doing five unrelated things hurts testability. So the first indexing step splits documents into smaller, retrievable pieces, taking care not to cut mid-sentence or across a semantic unit. Each chunk carries metadata (title, source, page, section) so whatever gets retrieved stays traceable — directly addressing the "no source attribution" pitfall from §3.

Python note

RecursiveCharacterTextSplitter (LangChain) tries a sequence of natural split points — first paragraph breaks, then sentence breaks, then word breaks — recursively falling back to a harder cut only if a piece still doesn't fit. That's what "recursive" refers to: a fallback chain that respects the text's natural structure before resorting to a blunt character cut.

chunk_size caps piece length; chunk_overlap shares text across boundariestext_splitter = RecursiveCharacterTextSplitter( chunk_size=50, chunk_overlap=20, # overlap avoids losing context at chunk boundaries )

Without overlap, a sentence or idea falling right at a cut point could end up split so that neither resulting chunk contains the full thought — similar to an overlapping sliding window in a streaming system.

Embeddings

Once you have chunks, you need to compare their meaning numerically — a question and its answer often share almost no words in common, so string matching alone won't do. A naive encoding like one-hot vectors carries zero notion of similarity: "dog" and "puppy" end up exactly as "different" as "dog" and "spreadsheet." An embedding fixes this by learning a dense vector space — typically hundreds of dimensions — where semantically similar text ends up close together.

ModelSizeDim.Best for
all-MiniLM-L6-v222 MB384Lightweight, efficient general use
all-mpnet-base-v2110 MB768Higher accuracy, still fast
all-roberta-large-v1350 MB1024Larger multilingual datasets, slower
xlm-roberta-base550 MB768Multilingual text, less precise in English

The pattern here is the same accuracy/footprint trade-off you navigate elsewhere: a bigger model with more output dimensions captures more semantic nuance, at the cost of memory and slower embedding generation.

Python note

SentenceTransformer (from the sentence-transformers library) loads one of these pretrained models and exposes a simple call to turn text into its embedding vector — later, in this module's Sprint Exercise, loading all-MiniLM-L6-v2 and calling it on a chunk of text is literally how each 384-dimensional vector gets produced.

Retrieval: distance metrics

Once every chunk (and every incoming question) is a point in a high-dimensional vector space, "search" reduces to a geometry problem: find the points nearest to the query point.

MetricFormulaIntuition
Cosine distance1 − (A·B)/(‖A‖‖B‖)Angle between vectors
Dot productΣ Aᵢ·BᵢAlignment of two vectors
Squared EuclideanΣ (xᵢ−yᵢ)²Straight-line distance
Manhattan (L1)Σ |xᵢ−yᵢ|Sum of absolute differences

Cosine similarity measures the angle between two vectors while ignoring their length — this matters for text embeddings because a vector's magnitude often reflects incidental things like passage length rather than meaning, so measuring direction alone tends to be a more robust proxy for "these chunks are about the same thing." Squared Euclidean is the straight-line formula extended to many dimensions — it does care about magnitude. Manhattan sums absolute per-coordinate differences instead of squaring — the distance you'd travel moving only along a city grid. Dot product rewards both direction and magnitude at once.

Worked example

A chunk's embedding (toy-sized to 3 dimensions for hand computation) A=[1,2,3], a query's embedding B=[2,1,3]. Cosine similarity = (A·B)/(‖A‖·‖B‖).

  1. Dot productA·B = (1×2)+(2×1)+(3×3) = 2+2+9 = 13
  2. Magnitudes‖A‖ = √(1²+2²+3²) = √14 ≈ 3.742   ‖B‖ = √(2²+1²+3²) = √14 ≈ 3.742 (equal here since they're permutations of the same numbers)
  3. Cosine similarity13/(3.742×3.742) = 13/14 ≈ 0.929 — very close to 1, meaning the two vectors point in almost the same direction
  4. Cosine distance1 − 0.929 = 0.071 — correctly signaling "these are nearly the same" in a metric where smaller means closer

The chunk and query are highly related. If B had instead been [−1,−2,−3] — pointing the opposite direction — the dot product would be negative and cosine similarity would approach −1, correctly flagging dissimilarity even though the raw magnitudes are identical.

Gotcha

Cosine distance (1 − cos θ) is a dissimilarity score — smaller is more similar. Don't confuse it with cosine similarity itself (cos θ), where larger is more similar; a query engine that mixes these up ranks results in the exact opposite order it means to.

Storing potentially millions of embeddings and searching them fast enough for an interactive query is itself a systems problem — the job of a vector database. It plays the same role a specialized index (a B-tree, an inverted index) plays in a relational database: rather than brute-force comparing a query vector against every stored vector, it uses index structures purpose-built for high-dimensional approximate nearest-neighbor search, trading a small amount of exactness for a large speedup at scale.

Python note

Pinecone is one such hosted vector database. After chunks' embeddings are upserted into a Pinecone index, index.query(vector=question_vector, top_k=k, include_metadata=True) returns the k stored vectors closest to the query, along with similarity scores and metadata — conceptually similar to SELECT ... ORDER BY distance LIMIT k, except the underlying search is approximate nearest-neighbor rather than a full scan.

Generation

Retrieval alone gets you a ranked handful of relevant raw text chunks — not yet a written answer. The final step hands the original question and the retrieved chunks to an LLM and asks it to synthesize a coherent, cited response — the same task you'd give a human assistant handed a few relevant excerpts and asked to write up an answer. The assembled prompt typically combines three parts explicitly:

[User Question] How does the Marketing team make strategic decisions? [Context] - The Marketing team recently shifted focus to data-driven decision-making. - They rely on weekly reports and campaign retrospectives. - A/B testing, customer segmentation, and performance metrics. [Instruction] Using the provided context, answer the question concisely and cite your sources.
Python note

OllamaLLM (used in this module's Sprint Exercise) is a thin wrapper around Ollama, a tool for running open-weight LLMs like Llama 3.2 directly on your own machine. Calling .invoke(prompt) sends the assembled prompt to that local model process and returns its generated text — no network call to a cloud LLM provider involved, making the exercise's pipeline entirely open-source and self-hosted end to end.

Test Yourself

Retrieval practice — the single best-evidenced study technique there is.

Cover the answer, try to recall it from memory, then click to check. Getting it wrong and then reading the answer still strengthens the memory — skipping straight to the answer doesn't. Do this before your exam, not while reading for the first time.

What makes next-token prediction "self-supervised," and why does that matter for how much data can be used to train on?

No human ever labels examples — the "label" for any position is just the next word already present in the text, so sliding a window across any document yields a free training example, turning an unlimited supply of unlabeled text into an unlimited supply of labeled training pairs.

In the worked context example for "…pass me the ___," what are P(Salt), P(Pepper), and P(Gun) in the tense confrontation scene, and what does comparing it to the family dinner scene illustrate?

Tense confrontation scene: P(Salt)=0.16, P(Pepper)=0.18, P(Gun)=0.66. Since the literal sentence never changed, only the surrounding context did — showing the model conditions on the entire preceding context rather than memorizing fixed word associations.

Per the module's gotcha callout, what determines the size of an LLM's output layer, and what two things does it explicitly NOT equal?

The output layer is a softmax over the entire vocabulary, so its size equals the vocabulary size — not the embedding dimension and not the context length.

In the seven-logit worked example, what probability does token E (logit 3.0) get at T=1.0, and what does it rise to at T=0.5?

At T=1.0, token E gets ≈0.449 (44.9%) of the probability mass; lowering the temperature to T=0.5 sharpens the distribution and raises E's share to 74.2%.

In that same worked example, what happens to token E's and token D's probabilities when temperature is raised to T=2.0 instead?

Token E drops from 44.9% (at T=1) to 28.1%, while the weakest token D climbs from 2.3% to 6.3% — higher temperature flattens the distribution so every token becomes more competitive.

Using the module's "runtime lookup vs. baked into the binary" analogy, how do RAG and fine-tuning differ in how they update a model's knowledge?

RAG retrieves relevant external documents at query time without changing model weights, like a service querying a live database on every request — update the data and the next query reflects it, no redeploy needed. Fine-tuning modifies the model's internal weights via further training, closer to compiling business rules directly into the binary — fast and consistent at inference, but requires retraining and redeploying to update.

For the toy embeddings A=[1,2,3] and B=[2,1,3], what is the dot product, the magnitude of each vector, and the resulting cosine similarity?

A·B = (1×2)+(2×1)+(3×3) = 13, and ‖A‖=‖B‖=√14≈3.742 (equal since they're permutations of the same numbers), giving cosine similarity = 13/14 ≈ 0.929 — very close to 1, meaning the vectors point in almost the same direction.
