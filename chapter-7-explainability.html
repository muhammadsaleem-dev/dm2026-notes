1

Why Explainability Matters

For most of software engineering history, "correct" and "understandable" were the same property — you could read the code, or step through it in a debugger, and see exactly why it did what it did. Machine learning breaks that assumption. A random forest or a neural network arrives at a prediction through millions of numeric operations across hundreds of learned parameters, and there is no line of "business logic" you can point to and say "this is why." That gap — a model that works but can't explain itself — is the whole reason explainability exists as a field.

Who needs an explanation, and why

Take a loan-approval model as the running example. Four different people interact with it, and none of them are asking the same question:

Stakeholder (loan approval)Their question
Domain user (loan officer)"Why is this client risky? Can I trust this model?"
Developer"Why does the model behave this way? How do I fix an error?"
Auditor"Are minority groups disproportionately denied? Is it using appropriate factors?"
End user"Why was my loan denied?"

A single number — "predicted probability of default: 0.82" — answers none of these on its own. Explainability techniques exist precisely to translate "the model computed 0.82" into an answer shaped for whichever audience is asking.

The trade-off: accuracy vs. explainability

The models easiest to explain tend to be the least accurate on hard problems, and the most accurate tend to be hardest to explain. A decision tree with five splits is fully interpretable — print it out and read it like a flowchart — but often can't capture the subtle, high-dimensional patterns a deep neural network can. The network might get you 15% better accuracy, but its internal representation is a black box of matrix multiplications no human can read directly.

This isn't a trade-off you resolve once and forget. A model recommending which ad to show has little at stake if it's a bit unexplainable. A model that denies a mortgage or flags fraud is different entirely. The right balance depends on ROI and compliance requirements, not just raw performance.

Rule

Explainability matters most when decisions affect people's lives (healthcare, finance, justice), when regulation demands transparency, or when trust is the product. It matters less for low-stakes decisions where speed/accuracy dominate.

2

Two Axes of Explainability

Before looking at specific techniques, it helps to have vocabulary for classifying them — otherwise "explainability" becomes a vague catch-all. There are two independent questions you can ask about any explanation technique: what scope does it explain (one prediction, or the whole model), and where does the explanation come from (built into the model, or bolted on afterward)?

Local vs. global

Think of the difference the way you'd think about debugging a single failing test versus reading a code-coverage report for the whole suite.

LocalGlobal
GoalExplain one predictionUnderstand overall model behavior
Answers"Why this output for this instance?""What features matter overall?"
Useful forCase-by-case review, debugging one surprising resultFeature selection, monitoring, auditing
ExamplesSHAP force plot, LIME, counterfactualsFeature importance ranking, SHAP summary plot

Back to the loan example: the end user ("why was my loan denied?") needs a local explanation — a story about their specific application. The auditor ("are minority groups disproportionately denied?") needs a global explanation — a pattern across thousands of applications.

A developer asks "why does the model behave this way, and how do I fix an error?" — local or global?

Usually global — debugging systematic behavior means understanding patterns across many predictions, not just one. (Though tracking down one specific surprising prediction would be a local question — scope depends on exactly what's being asked.)

Some techniques, like SHAP, can actually be used at both scopes.

Inherent (glass-box) vs. post-hoc (black-box)

The second axis is about when the explanation is available. Some models are transparent by construction — the model's structure is the explanation. Others are opaque, needing an outside technique after the fact.

InherentPost-hoc
NatureTransparent, self-explanatoryOpaque; needs a separate interpretation technique
ExamplesLinear/logistic regression, shallow trees, rule-based modelsNeural nets, random forests, gradient boosting, high-dim SVM
Trade-offMay sacrifice accuracy on complex tasksKeeps performance; needs SHAP/LIME to gain insight

To make "inherent" concrete: in a decision tree, the order of splits already reveals feature importance — the first split is, by construction, the single most discriminating feature, because that's the criterion the tree-building algorithm optimizes at each node. In logistic regression, ŷ = σ(wᵀx + b), there's no separate interpretation step needed — the learned weight vector w is each feature's contribution, directly, as a number you can read off after training.

A random forest sits in an interesting middle ground: built out of individually inherently-explainable trees, but once you combine hundreds and average their votes, the ensemble's combined decision is no longer something a human can trace by hand.

🧠Inherent-vs-post-hoc is about individual model families, but nothing stops "inherently explainable" building blocks from combining into something that isn't — which is exactly why post-hoc methods like permutation importance and SHAP exist at all.

3

Permutation Feature Importance

If a feature matters, breaking it should hurt performance.

Suppose you've trained a random forest that gets 90% accuracy. You want to know which input features are actually doing the work — not because you can read the forest's 200 trees by hand, but because you need to answer "is this model relying on something inappropriate?" or "which features are worth the cost of collecting?"

The insight is refreshingly low-tech: if a feature genuinely matters, destroying the information in that feature should hurt performance. If a feature is irrelevant, scrambling it shouldn't change anything, since the model wasn't really using it. This is the ML equivalent of unplugging one wire in a circuit at a time to see which one makes the lights go out — you don't need the circuit diagram to learn something real from that experiment.

"Destroying the information" has a specific meaning: take one column — say, everyone's Age — and shuffle the values randomly among rows, leaving every other column exactly as it was. Each row now has a random person's age attached.

After shuffling the Age column, has the statistical distribution of ages in the dataset changed?

No — the same set of age values is still there, just reattached to the wrong rows. What's destroyed is the relationship between a person's real age and their other features and true outcome, not the raw numbers themselves.

Because this technique never looks inside the model — only shuffles inputs and reads outputs — it works identically for a decision tree, a random forest, a neural network, or anything else. That's what "model-agnostic" means in practice.

  1. Train the model; measure baseline performance s (e.g. 90% accuracy).
  2. Randomly shuffle one feature's column only, leaving everything else untouched.
  3. Re-evaluate → new score (e.g. 78%).
  4. Importance = baseline − new score (90% − 78% = 12%).
  5. Repeat K times per feature and average, to smooth out random variation; rank all features by their drop.

Step 5 exists because a single random shuffle is, well, random — you might get an unusually damaging (or harmless) shuffle by chance. Averaging several gives a more reliable estimate of the typical damage that feature's scrambling does.

Worked example

Using the loan-officer scenario: baseline accuracy is 90%.

Feature: Age. Shuffle the Age column, leave Income/Balance/Region/Gender untouched, re-run: accuracy drops to 78%.

importance(Age) = baseline − shuffled = 90% − 78% = 12%

A big drop — the model leans heavily on a person's real age lining up correctly with their real other features and outcome.

Feature: Income. Put Age back to normal, shuffle Income instead. Accuracy comes out to 83%:

importance(Income) = baseline − shuffled = 90% − 83% = 7%

Smaller drop than Age — the model relies on Income, but less heavily. Repeating for every feature:

FeatureScore after shufflingImportance (drop from 90%)
Age78%12%
Income83%7%
Balance86%4%
Region89%1%
Gender90%0%
Python note

sklearn.inspection.permutation_importance(model, X, y, scoring=..., n_repeats=...) does exactly the procedure above: shuffle one column at a time, re-score using whatever metric you pass to scoring, repeat n_repeats times per feature and average, and return every feature's importance in one call.

The scoring argument matters more than it looks. The whole procedure is built on "importance = baseline score − shuffled score," which only makes sense if a higher score means better — that's true for accuracy or F1 on a classifier, so those plug in directly. A regression target flips this: the natural metrics (RMSE, MAE) are error — lower is better — so a worse (shuffled) model would produce a higher RMSE, and subtracting would give a negative "importance" for every genuinely useful feature, backwards from what you want.

Python note

For a regression target, pass one of scikit-learn's negated error scorers instead — scoring='neg_root_mean_squared_error' or 'neg_mean_absolute_error' — so "higher is better" holds again (a worse model's negated error is a more negative, i.e. lower, number). permutation_importance then subtracts exactly the same way it does for classification, and the arithmetic keeps working.

Quiz

If shuffling a feature improves performance, does that mean the feature is useless? No — a negative importance means the model does better once that feature's information is destroyed, which points to noise, overfitting, redundancy, or a harmful learned dependency. That's a more serious finding than "useless": it suggests the model latched onto some spurious pattern involving that feature during training.

Pros: model-agnostic, simple enough to explain in one sentence: "we broke this column and performance got worse by X." Cons: correlated features can mask each other's importance — if Income and Balance are strongly correlated, shuffling Income alone doesn't remove much information, since the model can still infer roughly the same thing from Balance, so both can look artificially unimportant even though the pair matters a great deal. It's also expensive with many features, and can be unstable on small datasets.

4

Shapley Values (SHAP)

Borrowed from game theory: features are "players," the prediction is the "payout" to split fairly.

Permutation importance has a real weakness worth naming before introducing the fix: because it shuffles one feature at a time, it doesn't fairly account for features that only matter in combination, and it can be thrown off by correlation, as with Income and Balance above. What we actually want is a way to divide credit for a prediction among all contributing features — fairly, even when features interact and overlap — the way you'd divide profits among business partners who each contributed different, overlapping amounts of effort to a shared outcome.

That "divide credit fairly" problem was solved mathematically in 1953, in game theory, by Lloyd Shapley, for how to split a payout among collaborating players when different subsets ("coalitions") could have achieved different value on their own. SHAP (SHapley Additive exPlanations) borrows that solution wholesale: the "players" become your model's features, the "payout" becomes the model's prediction for one specific instance.

Marginal contribution: the core idea

The building block is the marginal contribution of a feature — "how much does adding this feature to a group of already-known features change the prediction?" If you already know an applicant's Income, and I additionally tell you their Credit Score, the prediction moves by some amount — that movement, given Income was already known, is Credit Score's marginal contribution.

The catch: a feature's marginal contribution generally depends on what other features were already present. So there's no single "the" marginal contribution — there's a whole family of them, one per possible subset of other features. Shapley's insight: the fair way to give one feature one clean number is to compute its marginal contribution for every possible subset and every possible order those features could have been revealed in, then average all of those, weighted so no ordering unfairly dominates.

The formula, unpacked

φᵢ(v) = Σ_{S⊆N\{i}} [ |S|!·(n−|S|−1)! / n! ] · ( v(S∪{i}) − v(S) )

This looks intimidating mostly because of the factorial weighting term. N\{i} means "all features except feature i" — the set subsets S are drawn from. v(S) is the model's prediction using only the features in S (the rest held at a neutral/average baseline). v(S∪{i}) − v(S) is the marginal contribution described above. The fraction |S|!·(n−|S|−1)!/n! is a weight — precisely the probability that, if you lined up all n features in a uniformly random order, the features in S would appear before feature i and everything else after. The whole formula is a weighted average of "how much does feature i add, across every point in every possible ordering."

Worked example

Formulas are easiest to trust once you push real numbers through by hand, so here's the smallest non-trivial case: a toy loan-approval model with only two features, Income and Credit Score, for one applicant. Define v(S) as "the model's predicted approval probability (%) when only the features in S are known, with any unknown feature replaced by its dataset-average value." There are exactly four subsets of a two-feature set:

  • v(∅) = 50 — knowing nothing beyond the population average, prediction is 50%.
  • v({Income}) = 70 — knowing just their (high) Income, prediction rises to 70%.
  • v({CreditScore}) = 60 — knowing just their (decent) Credit Score, prediction rises to 60%.
  • v({Income, CreditScore}) = 90 — knowing both, the full model's actual prediction is 90%.

With two features, there are exactly two orderings: (Income, then Credit Score) or (Credit Score, then Income).

  1. Income's marginal contribution, revealed firstadded to the empty set: v({Income}) − v(∅) = 70−50 = 20
  2. Income's marginal contribution, revealed secondafter Credit Score is known: v({Income,CreditScore}) − v({CreditScore}) = 90−60 = 30
  3. Average → φ_Income(20+30)/2 = 25
  4. Credit Score's marginal contribution, revealed firstv({CreditScore})−v(∅) = 60−50 = 10
  5. Credit Score's marginal contribution, revealed secondafter Income is known: v({Income,CreditScore})−v({Income}) = 90−70 = 20
  6. Average → φ_CreditScore(10+20)/2 = 15

Checking this against the formula's factorial weights directly (not just the "average over orderings" shortcut): for n=2, subsets of N\{Income} are ∅ (size 0) and {CreditScore} (size 1).

  1. Factorial weightsWeight for size 0: 0!·(2−0−1)!/2! = 1/2   Weight for size 1: 1!·(2−1−1)!/2! = 1/2
    Both come out ½ — with only two features, "average over orderings" and "average over subsets" coincide
  2. Plug into the formulaφ_Income = (1/2)·(v({Income})−v(∅)) + (1/2)·(v({Income,CreditScore})−v({CreditScore}))
    = (1/2)·20 + (1/2)·30 = 10 + 15 = 25 — matching the hand-averaged answer
  3. Efficiency check 1: values sum to the total swingφ_Income+φ_CreditScore = 25+15 = 40, and indeed v({Income,CreditScore})−v(∅) = 90−50 = 40 ✓
  4. Efficiency check 2: baseline + values reproduce the prediction50+25+15 = 90 — exactly v({Income,CreditScore}) ✓

Both checks hold as a matter of mathematical guarantee (the efficiency property), not coincidence.

Reading a SHAP output

The identity from the worked example generalizes exactly: final prediction = base value + Σ SHAP values, where the base value is the model's average prediction across the whole dataset (our v(∅)=50) and each feature's SHAP value is its φᵢ. This is what makes SHAP genuinely additive — the contributions literally add up to the prediction, unlike a bare feature-importance ranking with no such guarantee.

  • A summary/bar plot (global) ranks features by mean |SHAP value| across every instance — collapsing per-instance numbers into one global ranking, similar in spirit to the permutation-importance ranking from §3, but via this fairer, interaction-aware allocation.
  • A beeswarm plot (local, per-instance) shows every data point's SHAP value (impact) and its actual feature value (color) — revealing both magnitude and direction together, so instead of just "Credit Score matters" you can see high credit scores push predictions up and low ones push them down, across every individual applicant.
Python note

shap.TreeExplainer(model) builds an explainer specialized for tree-based models (random forests, gradient boosting) that computes exact Shapley values efficiently by exploiting the tree structure, rather than brute-forcing every subset. explainer.shap_values(X) runs that computation across a whole dataset and returns the per-feature, per-instance SHAP values used to draw the plots above.

Key warning

SHAP values do not reflect causality. A high-importance feature (e.g. Titanic "Fare") is useful for prediction, but may just be capturing information about a different real cause — it doesn't mean changing that feature would change the outcome. Predictive importance ≠ actionability. A large SHAP value tells you the model used that feature heavily and that it's statistically associated with the outcome — it does not tell you that manipulating the real-world value would change the real-world outcome. That's §5's entire subject.

5

Causality: Beyond Correlation

Explainability says what the model used. Causality asks what would actually change the outcome.

Every technique so far — inherent interpretability, permutation importance, SHAP — answers some version of "what did the model use to make this prediction?" That's a question about the model. It's a genuinely different question from "what, in the real world, would actually change the outcome if I changed it?" — and conflating the two is one of the easiest and most consequential mistakes to make with any of these tools. A feature can dominate a SHAP summary plot and still be something you could set to any value you like without changing a single real outcome.

Causal inference, counterfactuals, and interventions

  • Causal inference asks, directly, does X cause Y? — using statistical techniques (randomized experiments, natural experiments, causal graphs) designed to isolate causation from mere association.
  • Counterfactual analysis asks "what if?" — for this specific case, what would have happened had one input been different, holding everything else fixed?
  • Interventions simulate an action and observe the effect — rather than passively watching existing data, you reach in and change one variable, then measure downstream effects.

This matters most for decisions you actually intend to act on: treatment choices in medicine, policy changes in government, pricing in business — anywhere the whole point is to decide what to do, not just predict what happens if nothing changes.

Confounders — the trap explainability alone can't see

The mechanism by which explainability gets this wrong has a name: a confounder is a hidden variable that influences both the feature your model latched onto and the outcome you're predicting, creating a strong statistical association between the two even though neither causes the other.

  • Umbrellas & accidents: a model finds umbrella ownership predicts traffic accidents. The real cause is rain, which drives both. Handing out umbrellas would not reduce accidents. Deliberately silly, so the pattern is unmistakable.
  • Titanic — Sex: explainability ranks "sex" as the top predictor of survival. The real cause was the unrecorded "women and children first" evacuation policy — sex didn't cause survival, it correlated with who got lifeboat access. The confounder isn't even a column in the dataset — it's an unrecorded real-world process that left a strong statistical fingerprint on a column that was recorded.
  • Titanic — Fare: explainability ranks fare as important, but higher fare really just correlated with passenger class — cabins closer to lifeboats, faster crew assistance. The model reaches for the nearest available proxy (price paid), and SHAP faithfully reports it as important, because it is useful for prediction — even though paying more money didn't, by itself, save anyone's life.

The pattern across all three: an explainability technique will correctly and honestly tell you which feature the model is using, because that is exactly what it's designed to measure. It cannot tell you whether that feature is a real cause or merely a bystander correlated with the real cause.

Explainable AICausal AI
Makes model decisions understandableUncovers real cause-and-effect, beyond correlation
Reasons from patterns already in the dataValidates real-world causal links via inference/experiments/domain knowledge
"What factors influenced this decision?""What would happen if we intervened on this factor?"

Use SHAP and permutation importance to understand and debug your model, to audit it for inappropriate reliance on sensitive features, and to build trust with stakeholders. But the moment the question changes from "how does the model decide" to "what should we actually change in the real world," you've left explainability's territory and need causal tools instead — no amount of re-running SHAP on the same dataset will answer that second question for you.

Test Yourself

Retrieval practice — the single best-evidenced study technique there is.

Cover the answer, try to recall it from memory, then click to check. Getting it wrong and then reading the answer still strengthens the memory — skipping straight to the answer doesn't. Do this before your exam, not while reading for the first time.

In the loan-approval example, what specific question does the auditor ask, and how does that differ in scope from the end user's question?

The auditor asks "Are minority groups disproportionately denied? Is it using appropriate factors?" — a global question about patterns across many applications. The end user asks "Why was my loan denied?" — a local question about one specific instance.

Why is a random forest described as sitting in a "middle ground" between glass-box and black-box models?

It's built out of individual decision trees that are each inherently explainable, but once hundreds of trees are combined and their votes averaged, the ensemble's combined decision can no longer be traced by hand — which is why post-hoc methods like permutation importance and SHAP are needed for it.

In the permutation importance worked example, the baseline accuracy is 90%. What was the accuracy after shuffling the Age column, and what importance value does that produce?

Accuracy dropped to 78% after shuffling Age, giving an importance of 90% − 78% = 12%.

In the same worked example, what accuracy resulted from shuffling Income instead of Age, and what does the comparison to Age's importance suggest?

Shuffling Income dropped accuracy to 83%, an importance of 7% — smaller than Age's 12%, meaning the model relies on Income but less heavily than on Age.

In the 2-feature Shapley value worked example (Income and Credit Score), what are the four values of v(S) for the four possible subsets?

v(∅) = 50, v({Income}) = 70, v({CreditScore}) = 60, and v({Income, CreditScore}) = 90.

What are the computed Shapley values φ_Income and φ_CreditScore in the worked example, and how does the efficiency property check out against v(∅) and v({Income, CreditScore})?

φ_Income = 25 and φ_CreditScore = 15. Efficiency checks: they sum to 40, matching v({Income,CreditScore}) − v(∅) = 90 − 50 = 40; and adding them to the base value gives 50 + 25 + 15 = 90, matching v({Income,CreditScore}) exactly.

According to the "Key warning" callout in the SHAP section, what does a large SHAP value actually tell you, and what does it NOT tell you?

A large SHAP value tells you the model used that feature heavily and that it's statistically associated with the outcome. It does not tell you that manipulating the real-world value of that feature would change the real-world outcome — SHAP values do not reflect causality.

In the Sprint Exercise, which single feature dominated across all three explainability methods (impurity-based feature_importances_, permutation importance, and SHAP), and what pattern did the beeswarm plot reveal about it?

The feature "sex" dominated all three methods. The beeswarm plot showed female (low-encoded) values pushing predictions toward survival and male values pushing away from it, reflecting the "women and children first" pattern.

You're computing permutation importance for a regression model that predicts house prices, and you pass scoring='neg_mean_absolute_error' instead of a plain MAE. Why the minus sign?

Permutation importance is defined as baseline score minus shuffled score, which only gives a sensible positive number for a genuinely useful feature if "higher score = better." MAE is an error — lower is better — so a worse (shuffled) model would produce a higher raw MAE, making the subtraction come out backwards. Negating the metric restores "higher is better" so the same arithmetic works for regression as it does for classification accuracy or F1.

In a churn-prediction SHAP beeswarm plot, high values (red) of "monthly_charges" cluster on the positive side of zero, while high values of "tenure_months" cluster on the negative side. What does each feature's pattern tell you about churn risk?

High monthly charges push the prediction toward churn (positive SHAP = higher predicted churn probability), while long tenure pushes the prediction away from churn (negative SHAP = lower predicted churn probability) — customers who've stuck around longer are predicted less likely to churn, while a bigger bill increases predicted churn risk.

Exam Drill

Same skills as Test Yourself, but in the exam's actual answer format.

Real exams rarely ask you to write a paragraph — they ask you to name a technique in a couple of words, reorder scrambled steps, pick every correct item from a list, or fill in one line of code. These drills train that exact shape of answer, not just the underlying concept.

Name it A model's own coefficients or split structure fully explain its predictions, with no extra tool needed. In ≤2 words, what kind of model is this?

Glass-box (model). Linear/logistic regression and a single decision tree are the canonical examples — you can read the explanation straight off the trained model (§2).

Reorder Put these permutation-importance steps in order:
  1. A. Shuffle one feature's column, leaving all others untouched
  2. B. Re-evaluate the model's score on the shuffled data
  3. C. Train the model and record its baseline score
  4. D. Importance = baseline score − shuffled score
  5. E. Repeat for K shuffles per feature and average

C, A, B, D, E — baseline first, then shuffle → re-score → subtract → repeat and average per feature (§3).

Select all Which of these are LOCAL explanations (about one specific prediction), not global ones?
  • (a) a SHAP force plot for one applicant's loan decision
  • (b) a permutation-importance ranking across the whole test set
  • (c) "why was my loan denied?"
  • (d) a SHAP summary/bar plot ranking features overall

(a), (c). Both are about a single instance. (b) and (d) summarize behavior across many predictions — that's the global scope (§2).

Code Complete this call to compute permutation importance for a regression model, using a metric where higher is better: permutation_importance(model, X_test, y_test, scoring=____, n_repeats=10)

scoring='neg_mean_squared_error' (or 'neg_root_mean_squared_error') — negating the error metric restores "higher is better" so the baseline-minus-shuffled subtraction works correctly (§3).

Code You've run result = permutation_importance(...), giving you result.importances_mean (one score per feature) and a list feature_names. Complete this to get the names of the top 3 most important features: top3 = pd.Series(result.importances_mean, index=feature_names).nlargest(____).index.tolist()

nlargest(3) — wrap the importance scores in a pandas Series indexed by feature name, then .nlargest(3) keeps only the 3 highest-scoring entries, and .index.tolist() pulls out just their names (§3).

Compute Toy 2-feature model: v(∅)=40, v({A})=55, v({B})=50, v({A,B})=70. Compute the Shapley value φ_A.

A revealed first: v({A})−v(∅) = 55−40 = 15. A revealed second: v({A,B})−v({B}) = 70−50 = 20. Average: φ_A = (15+20)/2 = 17.5 (§4).

Reorder Order the steps required to calculate feature importance via permutation:
  1. Subtract the corrupted metric from the baseline metric to determine the feature's importance score.
  2. Train a base model and evaluate its baseline performance metric on a validation set.
  3. Use the model to predict outcomes on this newly corrupted dataset.
  4. Restore the column and repeat for the next feature.
  5. Randomly shuffle the values in that single column, destroying its relationship with the target.
  6. Select a single feature column to evaluate.
  7. Calculate the new performance metric.

2, 6, 5, 3, 7, 1, 4 — Train base model → select feature → shuffle its values → predict again → calculate new metric → subtract from baseline → restore and repeat.
