Decision Trees

Classification is supervised learning: learn the pattern linking features to a known label, then apply it to new, unlabeled instances.

Before any of the machinery below makes sense, it's worth asking why decision trees exist at all. Plenty of classifiers — logistic regression, k-NN, SVMs — draw some kind of dividing line (or curve) through feature space. A decision tree does something much closer to how a person actually reasons through a diagnosis or a triage checklist: ask one question, look at the answer, ask the next question conditioned on that answer, and so on until you're confident enough to commit to a label. There's no hidden weight vector, no distance metric — just a nested sequence of "if this, then that" tests you could, in principle, print out and follow with a pencil.

Structurally, a tree is built from nodes (attribute tests, e.g. "does it fly?"), branches (the possible outcomes of that test), and leaves (a class prediction, or a probability split if the leaf isn't pure). The objective driving every split decision is simple to state: ask as few questions as possible while still generalizing well to data you haven't seen. That leaves one real engineering question: at any node, out of all the attributes you could test next, which one should you pick?

Choosing the best split: entropy & information gain

Imagine you're playing a guessing game: you have records with unknown class labels, and you're allowed to ask yes/no questions about their attributes to narrow things down. Some questions are worthless — if every record already has the same color, asking about color tells you nothing new. Other questions are extremely informative — if "does it fly?" perfectly separates birds from mammals, that one question does almost all the work. Decision trees need a precise, numeric way to measure "how informative is this question," so the algorithm — not a human — can decide, at every node, which attribute to test next. That numeric yardstick is entropy, and the quantity built on top of it is information gain.

Entropy measures how "mixed up" or unpredictable a set of labels is. If a set is pure (every record is the same class), entropy is 0. If a set is a 50/50 mix of two classes, entropy is at its highest value (1, in "bits," using log base 2):

entropy(X) = − Σᵢ pᵢ · log₂(pᵢ)

Why base 2? Because entropy is measured in bits — literally, the expected number of yes/no questions you'd need to identify a record's class if you asked optimally. A 50/50 split needs exactly 1 well-chosen question on average, hence entropy 1. If your calculator only has natural log, use log₂(p) = ln(p) / ln(2).

Information gain answers the question we actually care about: if I split X on attribute a, how much less mixed-up are the resulting subsets, on average, compared to before?

gain(X, a) = entropy(X) − Σ_{v ∈ Values(a)} (|X_v| / |X|) · entropy(X_v)

The attribute chosen is whichever maximizes this quantity — the split that reduces uncertainty the most.

Worked example

A small 7-record dataset — 4 birds and 3 mammals — reproduces the two headline numbers to remember: splitting on color gains only 0.020 bits, while splitting on fly gains 0.521 bits.

    log₂(4/7) = ln(0.5714)/ln(2) ≈ −0.8074   log₂(3/7) = ln(0.4286)/ln(2) ≈ −1.2224
    entropy(X) = −(0.5714×−0.8074) − (0.4286×−1.2224) = 0.4613 + 0.5239 = 0.9852 bits
  2. Split on flyFly=Yes = {eagle, pigeon, hawk} — all Birds, pure → entropy = 0
    Fly=No = {penguin, cat, whale, horse} — 1 Bird, 3 Mammals (p=1/4, 3/4)
    log₂(1/4) = −2.0000 (exact),   log₂(3/4) ≈ −0.4150
    entropy(Fly=No) = −(0.25×−2.0) − (0.75×−0.4150) = 0.5 + 0.3113 = 0.8113
    Weighted average: (3/7)×0 + (4/7)×0.8113 = 0.4636 → gain(X, fly) = 0.9852 − 0.4636 = 0.5216 ≈ 0.521 bits
  3. Split on color, for comparisonColor=Brown = {eagle, hawk, cat} (2 Bird, 1 Mammal), entropy ≈ 0.9183
    Color=White = {pigeon, penguin, whale, horse} — dead-even 2/2 split, entropy = 1.0000 (the maximum possible)
    Weighted average: (3/7)×0.9183 + (4/7)×1.0 = 0.9650 → gain(X, color) = 0.9852 − 0.9650 = 0.0202 ≈ 0.020 bits

Why the two attributes differ so much: fly manages to carve out a perfectly pure subgroup (all 3 flyers are birds), which is what makes the resulting weighted entropy drop so far. color never produces a pure subgroup — one branch is still a coin flip. That gap (0.521 vs. 0.020) is exactly what drives the tree to test fly at the root.

Python note

math.log2(x) computes log base 2 directly; for arrays, NumPy's np.log2(array) does it elementwise. You'll essentially never implement entropy/information-gain splitting yourself, though: sklearn.tree.DecisionTreeClassifier does it for you. Its criterion parameter selects the impurity measure — pass criterion="entropy" to use exactly the calculation above (the default, "gini", is a closely related, slightly cheaper impurity measure).

Overfitting, underfitting, and pruning

Nothing in the entropy/information-gain machinery stops a tree from splitting forever — in the limit, you could keep adding tests until every leaf contains exactly one training record, achieving zero training error by simple memorization. That tree is useless: it has learned the noise of this particular training set rather than the underlying pattern. If you plot error against tree complexity for both train and test sets: train error keeps falling as the tree grows (more splits can only help fit training data better), but test error falls at first, then rises once the tree begins fitting noise. The low point of the test curve — not the train curve — is the complexity level you actually want.

Failure modeWhat's happening
UnderfittingThe tree is too simple/shallow — it does poorly on both training and test data.
OverfittingThe tree is too complex — it fits training data (including noise) "parrot fashion," but that memorized detail doesn't transfer.

Regularization is the general name for any technique that penalizes model complexity specifically to head off overfitting — a word you'll meet again in every other model family in this bootcamp. For decision trees, the regularization technique is pruning: after growing a (possibly overly large) tree, remove nodes bottom-up whenever doing so decreases error on a held-out validation set, even though removing them will always make training error a little worse.

Limitations

IssueDescription
Overfitting riskBuilds overly complex trees on noise, worse with small/high-dimensional data
Lower predictive powerOften less accurate than ensemble methods (below)
InstabilitySmall data changes can produce a completely different tree — an early split near the root can cascade into an entirely different shape downstream
Axis-aligned splits onlyEvery test is "is feature X above/below a threshold?" so decision boundaries are always blocky, rectangular — never diagonal
Quiz

"Which plot shows a decision tree's decision boundary?" — the answer is always the one with blocky, axis-aligned rectangular regions, never smooth or diagonal ones. That boxiness comes directly from every split testing exactly one feature against one threshold — nothing in the model can express "a weighted combination of two features."

Python note
from sklearn.tree import DecisionTreeClassifier
clf = DecisionTreeClassifier(criterion="entropy", min_samples_leaf=3)
clf.fit(X, y)
clf.feature_importances_   # how much each feature reduced impurity, overall
clf.tree_                  # the underlying fitted tree structure

min_samples_leaf=3 is a pre-pruning control — it stops the tree from ever creating a leaf with fewer than 3 records, a cheap way to cap complexity without a separate post-hoc pruning pass. Gotcha: scikit-learn's trees only accept numerical features — categorical strings need encoding (one-hot or ordinal) first.

Random Forests

Growing many different trees on purpose, then letting them vote.

The Limitations table above ended on a real problem: a single decision tree is unstable and often mediocre compared to other approaches. The fix is almost paradoxical at first glance: instead of trying to build one really good tree, build many deliberately different, individually mediocre trees, and combine their predictions. This is an instance of a bigger idea — ensemble learning — and it works because the individual trees' errors tend to be uncorrelated: one tree's idiosyncratic mistake gets outvoted by all the other trees that didn't see that noise.

The catch: if you train several trees on the exact same data with the exact same algorithm, the greedy, deterministic split-selection process typically gives you the same tree back every time — there's nothing to vote between. So Random Forests deliberately inject two separate sources of randomness to force the trees apart.

Two randomization mechanisms

  • Bagging (Bootstrap Aggregating) — for each of M trees, draw a training subset the same size as the original data by sampling with replacement. The same original record can be picked more than once (and some records get left out entirely) for a given tree.
  • Random Subspace Method — independently, restrict each tree so that at each split it's only allowed to consider a random subset of the features, not all of them.

Random Forest = Bagging + Random Subspace + Decision Trees. At inference, a test record is pushed through every one of the N trees; each independently votes a class; the forest's answer is decided by majority vote. The proportion of trees that agree doubles as a confidence score — if 3 of 4 trees vote "Bird," the forest reports 75% confidence, with no extra calculation required.

Analogy: instead of giving one student 6 textbooks to summarize, split the class into small groups, each getting a different, overlapping subset of books and even different pages within those books. No individual group has the full picture, and a couple might genuinely misread their material — but the majority answer across the whole class is far more reliable than trusting any one student, because different groups' mistakes tend to be different mistakes and get outvoted.

Worked example

Take the 7-animal table from §1.

  1. Tree #1's bootstrap sample{eagle, eagle, penguin, cat, whale, whale, horse} — eagle and whale each appear twice, while pigeon and hawk don't appear at all in this tree's training data
  2. Tree #2's bootstrap sampleA different resample entirely: {pigeon, hawk, hawk, penguin, penguin, cat, horse}
  3. Random subspace at 1-of-2 features per splitTree #1 might only ever test fly at its root (never seeing color), while Tree #2 is restricted to color — the two trees end up structurally different purely from these two injected randomizations
  4. Forest vote (N=100 trees)82 vote Bird, 18 vote Mammal → the forest predicts Bird with 82% confidence
Python note
from sklearn.ensemble import RandomForestClassifier
clf = RandomForestClassifier(n_estimators=20)  # 20 trees

n_estimators is the number of trees N (bagging and random-subspace sampling are handled internally and on by default). More trees generally means a smoother, more stable vote at the cost of more computation — the Sprint Exercise below shows just how much dropping n_estimators from 1000 to 10 can hurt accuracy.

Adaptive Boosting (AdaBoost)

Instead of many independent trees, build weak learners sequentially, each one fixing the last one's mistakes.

Random Forest's whole strategy is parallel and independent: grow many trees separately, only combine them at the end via a vote. That's powerful, but none of the trees ever get told which specific records the other trees are struggling with. AdaBoost takes the opposite strategy: build a sequence of very simple models, one at a time, where each new model is deliberately trained to focus on exactly the examples the previous models got wrong.

Because each round only needs to nudge the ensemble a little further, the individual models are typically decision stumps: a tree of depth 1, a single yes/no test on a single feature. A stump alone is barely better than a coin flip, but a weighted sequence of dozens of stumps, each patching the previous ones' blind spots, can become a very strong classifier.

  1. Initialize weights — every one of N samples starts with equal weight 1/N. Weight represents "how much this example currently matters" when scoring the next stump.
  2. Train a stump, compute its say (α):
    αᵢ = ½ · ln((1 − εᵢ) / εᵢ)
    where εᵢ is the stump's weighted error rate. As εᵢ → 0 (a great stump), α grows large and positive — it gets a loud voice. As εᵢ → 0.5 (a useless stump), α → 0 — it's effectively silenced. If a stump does worse than random (ε>0.5), α goes negative, inverting its vote.
  3. Reweight samples — correctly-classified samples shrink (×e⁻ᵅ), misclassified ones grow (×e^α), then renormalize so weights sum to 1.
  4. Resample the next round according to the updated weights, so the next stump is forced to pay attention to this round's failures.
  5. Repeat for T rounds.

Final prediction is a vote weighted by each stump's α, not a simple majority:

C*(x) = argmax_y Σᵢ αᵢ · [Cᵢ(x) = y]
Worked example (illustrative toy — not from real data)

Suppose 5 training samples, initial weights all 1/5 = 0.2. The first stump gets 4 of 5 right, 1 wrong.

  1. Weighted errorAll weights currently equal 0.2 → ε = 0.2 (just the misclassified sample's weight)
  2. Compute αα = ½·ln((1−0.2)/0.2) = ½·ln(4) = ½×1.3863 = 0.6931
  3. Reweight each samplee⁻ᵅ = 4^(−½) = 1/√4 = 0.5 exactly → each correct sample: 0.2×0.5 = 0.1
    e^α = 4^(½) = √4 = 2 exactly → the misclassified sample: 0.2×2 = 0.4
    Total before renormalizing: 4×0.1 + 0.4 = 0.8
  4. Renormalize (divide by 0.8)correctly-classified: 0.1 / 0.8 = 0.125 (×4 samples)
    misclassified: 0.4 / 0.8 = 0.5
    check: 4 × 0.125 + 0.5 = 1.0 ✓

Going into round 2, the single sample the first stump got wrong now carries half of the entire dataset's weight — even though it's just 1 of 5 records. One wrong answer, reweighted by a factor of 4 relative to the right answers (0.5 vs. 0.125), dominates the next round's training signal.

Random Forest vs. AdaBoost

DimensionRandom ForestAdaBoost
TreesFull trees (depth is a hyperparameter)Almost always stumps (depth 1)
ComputationParallel — trees are independentSequential — each stump depends on the last
SamplingBagging: independent random subsetsBoosting: reweighted toward past mistakes
VotingEqual vote per treeWeighted vote, via α
OverfittingMore robust — bagging reduces varianceMore prone — keeps re-fitting to hard/outlier points
OutliersLess sensitive (averaging)Sensitive — an outlier keeps getting misclassified and keeps gaining weight, round after round
Trade-off

Random Forest is robust and broadly reliable, but harder to explain any single prediction from (it's an average over potentially hundreds of trees). AdaBoost can reach very high accuracy by successively refining simple rules, but that same sequential, corrective process makes it more easily thrown off by unusual or mislabeled records.

Ensemble learning, summarized: Bagging = same algorithm, different random data samples, trained independently. Random Subspace = same algorithm, different random feature subsets. Boosting = a sequence of models, each explicitly correcting the previous one's mistakes via reweighting.

Python note

Just as RandomForestClassifier packages up bagging + random subspace, sklearn.ensemble.AdaBoostClassifier packages up everything above — weight initialization, per-round stump fitting, α computation, and reweighting are all handled internally by .fit(X, y). You supply n_estimators for the number of boosting rounds T.

A First Look at Explainability & Causality

This chapter's closing detour — developed in full in Module 7.

Everything covered so far has been about getting a model to predict the right label. But in a lot of real deployments, "predicts correctly" is necessary but not sufficient — you also need to answer why the model predicted what it did. A bank that denies a loan, a hospital that flags a patient as high-risk, or a court using a risk score in sentencing all face the same requirement: a human is entitled to know what drove that specific decision. Explainable AI (XAI) is the umbrella term for techniques that make a model's individual predictions transparent.

Explainable AI

Some model families are transparent by construction — you can read the decision logic straight off the trained model. A linear/logistic regression model's coefficients directly tell you how much each feature pushes the prediction. A single decision tree's path from root to leaf is a plain-English explanation. These are glass-box models. Other families — Random Forests with hundreds of trees, neural networks, gradient boosting, high-dimensional SVMs — achieve strong accuracy precisely by combining huge numbers of small signals in ways too tangled to read off directly; these are black-box models, and getting an explanation out of them requires dedicated post-hoc techniques (Module 7).

Glass-box (interpretable)Black-box (opaque)
Linear / Logistic Regression, Decision Tree, k-NN, Naive Bayes, low-dim SVMRandom Forest, Neural Nets, Gradient Boosting, high-dim SVM
Worked example

A deliberately simplified glass-box model — a toy linear credit-scoring formula:

score = 2.5 + 0.00004 × income − 0.9 × missed_payments approve if score > 0

For an applicant with income = $40,000 and 3 missed payments:

income contribution: 0.00004 × 40,000 = +1.6 missed_payments contribution: −0.9 × 3 = −2.7 intercept: +2.5 score = 2.5 + 1.6 − 2.7 = 1.4 → score > 0, so: approved

Because the model is glass-box, you can hand the applicant the actual breakdown: income pushed the decision up by 1.6, missed payments pulled it down by 2.7, the baseline intercept contributed 2.5. If a 500-tree Random Forest had made the same "approved" call, you'd have no equivalent breakdown available directly from the model — you'd need a separate explainability technique layered on top. Note the callback: clf.feature_importances_ from §1 is exactly this kind of explanation applied to tree ensembles — how much each feature contributed to reducing impurity, in aggregate (rather than a per-prediction breakdown like the one above).

Causal AI

Causal AI pushes a step further than explainability. Explainability tells you which features the model used — it does not tell you whether those features actually cause the outcome, or merely happen to be correlated with something else that does. A model can be perfectly explainable while still being causally wrong about the world.

Worked example

Suppose you're studying patient survival time and treatment timing, and observe the following (illustrative) numbers:

GroupN patientsAvg. disease severity (1–10)Avg. survival (months)
Treated early103.234
Treated late107.819

Read naively, this says "early treatment causes 15 extra months of survival" — and a predictive model would happily learn "treatment timing" as an important feature. But look at the severity column: patients treated early were, on average, far less sick to begin with (3.2 vs. 7.8) — likely caught by routine screening rather than diagnosed after symptoms progressed. Severity independently affects both when treatment happens and how long the patient survives — it's a confounder. Some (perhaps most) of that 15-month gap may simply be "healthier patients get treated earlier and healthier patients survive longer regardless of timing," not "earlier treatment causes longer survival." A model that only sees correlations can't tell these stories apart; only causal analysis — deliberately accounting for the confounder — can.

Explainable AICausal AI
FocusMaking a decision understandableUncovering true cause-and-effect
MethodFeature importance, attention, decision treesCausal inference, domain knowledge, experiments
Answers"What factors influenced this decision?""What would happen if we intervened on X?"

The distinction in that last row is the one to hold onto: explainability answers a question about the model ("what did you use to decide this?"), while causal inference answers a question about the world ("if I actually changed X, what would happen to Y?"). Scikit-learn — and ML tooling generally — is built almost entirely around the first question; answering the second requires a different toolkit, which is exactly where Module 7 picks up.

Exercise 6 — Classification Pipeline with a Random Forest

Predicting cancer_type from cell-nuclei measurements and age (398 records). The notable part isn't the model — it's the discipline around it: a config dictionary declares every preprocessing/hyperparameter choice up front, before any code touches the data.

Declare choices before writing pipeline codeconfig = { "missing_value_strategy": "replace_by_mean_cancer_type", "scaling_method": "StandardScaler", "RDF": {"n_estimators": 1000, "max_depth": 6, "min_samples_split": 2, "min_samples_leaf": 2, "max_features": 0.7, "class_weight": "balanced"} }

Outliers are flagged via IQR (computed on train only) and folded into the same imputation step as real missing values, rather than handled separately:

Q1, Q3 = X_train.quantile(0.25), X_train.quantile(0.75) IQR = Q3 - Q1 outlier_mask = (X_train < Q1 - 1.5*IQR) | (X_train > Q3 + 1.5*IQR) X_train = X_train.where(~outlier_mask, np.nan)
Result

RandomForestClassifier(n_estimators=1000, max_depth=6, class_weight='balanced') reached 90% test accuracy. The exercise then asks students to drop n_estimators to 10 and watch performance degrade — a direct feel for how much ensemble size (§2) actually matters.

Gotcha

The final "production" model is refit on train+test combined — at which point you explicitly lose the ability to measure its accuracy. The earlier test-set score is your only honest estimate of how it'll perform.

Test Yourself

Retrieval practice — the single best-evidenced study technique there is.

Cover the answer, try to recall it from memory, then click to check. Getting it wrong and then reading the answer still strengthens the memory — skipping straight to the answer doesn't. Do this before your exam, not while reading for the first time.

In the 7-animal worked example (4 birds, 3 mammals), what is entropy(X) for the whole dataset before any split?

entropy(X) ≈ 0.9852 bits, computed from p(Bird)=4/7≈0.5714 and p(Mammal)=3/7≈0.4286.

In that same worked example, what are the information gains from splitting on fly versus color, and why is the gap so large?

gain(X, fly) ≈ 0.521 bits versus gain(X, color) ≈ 0.020 bits. The gap is large because fly carves out a perfectly pure subgroup (all 3 flyers are birds), while color never produces a pure branch — one branch is still a coin flip (entropy 1.0).

In the Random Forest worked example with N=100 trees, if 82 trees vote "Bird" and 18 vote "Mammal" for a new test animal, what does the forest predict, and with what confidence?

The forest predicts Bird with 82% confidence — the proportion of trees agreeing doubles directly as the confidence score, with no extra calculation needed.

In the AdaBoost worked example, the first stump misclassifies 1 of 5 samples (ε = 0.2). What is α, and what do the correctly-classified and misclassified sample weights become after reweighting and renormalizing?

α = ½·ln(4) = 0.6931. After reweighting and renormalizing, each correctly-classified sample's weight becomes 0.125 and the misclassified sample's weight becomes 0.5.

For the toy credit-scoring formula (score = 2.5 + 0.00004×income − 0.9×missed_payments), what are the individual contributions and final score for an applicant with $40,000 income and 3 missed payments, and is the loan approved?

Income contributes +1.6, missed_payments contributes −2.7, and the intercept contributes +2.5, giving a total score of 1.4. Since 1.4 > 0, the applicant is approved.

In the causal-confounder worked example, early-treated patients survive an average of 34 months versus 19 for late-treated patients. What variable is identified as the likely confounder, and why does it undermine the naive "early treatment causes longer survival" conclusion?

Disease severity is the confounder — early-treated patients averaged severity 3.2 versus 7.8 for late-treated patients. Severity independently affects both when treatment happens and how long the patient survives, so the 15-month gap may largely reflect "healthier patients get treated earlier and survive longer regardless of timing" rather than a causal effect of timing.

What test accuracy did the Sprint Exercise's RandomForestClassifier(n_estimators=1000, max_depth=6, class_weight="balanced") reach on the cancer_type dataset, and what follow-up manipulation does the exercise ask students to try?

It reached 90% test accuracy. The exercise then has students drop n_estimators to 10 and observe how much performance degrades, to feel how much ensemble size matters.

You lose the ability to measure the refit model's accuracy, since no held-out data remains. The earlier test-set score, measured before that final refit, is your only honest estimate of real-world performance.
